## 三、逐项深挖

### 3.1 生产部署目标定案

**问题本质**：`/api/execute-workflow` 是动态 Node Route Handler（构建输出 `ƒ`），需要常驻 Node runtime、SSE 流式与服务端密钥；GitHub Pages 只能托管静态文件，二者物理不兼容。

**方案对比**：

| 方案 | 适配度 | 成本 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| GitHub Pages | ❌ 不支持 Route Handler / SSE / 服务端密钥 | 低 | 执行引擎完全不可用 | 仅可用于纯静态预览 |
| Vercel | ✅ 原生支持，SSE 开箱即用 | 低 | 函数超时/并发计费；`maxDuration=30` 已配置 | **备选/快速上线** |
| Docker + standalone | ✅ 完全可控，可接 Redis/反代/内网 | 中 | 需自管缓存、TLS、排水、扩缩容 | **主方案** |
| Cloud Run / Fly.io | ✅ 容器化 PaaS | 中 | 冷启动、SSE 需确认 LB 不缓冲 | 可作为 Docker 的托管替代 |

**已落地**：

1. `next.config.mjs` 开启 `output: "standalone"`，并为 `/api/execute-workflow` 增加 `X-Accel-Buffering: no` + `Cache-Control: no-store`。
2. 新增 `Dockerfile`（Node 22 + pnpm + 非 root + HEALTHCHECK + 多阶段）与 `.dockerignore`。
3. 新增 `GET /api/health`，返回 `status / version / uptimeSeconds / rateLimitStore`，不含任何密钥。
4. 以 standalone 产物实测：`node server.js` → `/api/health` 200、条件分支工作流正常返回。

**集群落位（按已提供设备矩阵）**：

| 服务 | 落位 | 关键约束 |
| --- | --- | --- |
| Next.js app | yyc3-45 Docker V3（NVMe RAID1） | 只绑定 Tailscale `100.65.172.88:3000` |
| Redis 限流 | yyc3-45 V3（compose 内置） | AOF + `noeviction`，仅内网 |
| PG15 主库 | **yyc3-45（已定案；数据放 V3 NVMe）** | 避免依赖 Mac 休眠；V2 HDD 不适合做数据盘 |
| PG15 备库 | **yyc3-22（已定案；流复制，5433）** | 只读/分析/DR；切换步骤见 005 手册 |
| 公网入口 | yyc3-33 ECS nginx | 仅 443 暴露；SSE 关缓冲 |
| 主/辅推理 | yyc3-n1 / yyc3-n2 | OpenAI 兼容端点，后续接 `model-resolver` |
| 冷备/演练 | yyc3-77 | 季度恢复演练 |
| Windows 兼容 | yyc3-66 | Edge/Chrome + 输入法/缩放 |

> 详细论证（含「本机主、NAS 辅」的风险、V1/V2 同池、5433 歧义）见 `docs/06-运维保障阶段/0601-运维策略/004-集群拓扑与部署映射.md`。
>
> **2026-11-11 已定案**：NAS（yyc3-45）主、Mac（yyc3-22）备，两台主机各监听 5433；切换与演练步骤见 `docs/06-运维保障阶段/0601-运维策略/005-PG15主备切换与演练手册.md`。

**必须遵守的运行时约束**（来源：Next.js 自托管文档）：

- 反向代理/负载均衡**逐跳关闭缓冲**，否则 SSE 会被攒批；
- 多实例统一 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 与 `deploymentId`；
- 多实例自定义 `cacheHandler`（Redis/S3），`revalidateTag` 才能全网失效；
- 收到 `SIGTERM` 给 10–30s 排水期，等待在途请求与 `after()` 完成；
- 服务端变量运行时求值，`NEXT_PUBLIC_*` 构建期内联（换环境需重建）。

**验收标准**：`docker build` 成功；容器 `HEALTHCHECK` 连续 3 次通过；SSE 首包 < 1s；滚动发布期间无 502。

### 3.2 工作流持久化与账号体系

**问题本质**：当前图只存在浏览器 `localStorage`，换设备即丢；执行 API 无身份概念，无法做配额、审计与团队协作。

**选型矩阵**：

| 维度 | Postgres + Drizzle | Postgres + Prisma | SQLite | MongoDB |
| --- | --- | --- | --- | --- |
| JSONB 图存储 | ✅ 原生 JSONB + GIN | ✅ 支持 | ⚠️ 弱 | ✅ 文档模型 |
| Serverless 驱动 | ✅ Neon/HTTP | ✅ Prisma 7 已改善 | ❌ | ✅ Atlas |
| 迁移可控性 | ✅ SQL 透明 | ✅ 成熟 | ✅ | ⚠️ |
| 团队上手 | 中 | 低 | 低 | 低 |

**推荐**：**PG15 自建 + Drizzle**。理由：图本质是 JSON 文档，但账号/运行记录需要强一致关系；JSONB 同时满足两者，且 Drizzle 的 SQL 透明性便于审计与性能调优。禁止接入 Supabase/Neon 等 BaaS，保持 PG15+Redis 自研架构。

**账号体系**：Auth.js 已进入维护模式，新项目在以下二选一：

| 方案 | 适用 | 成本 | 数据归属 |
| --- | --- | --- | --- |
| **Better Auth**（推荐） | 需要自托管、可控数据、后续 SSO/组织 | 中（约 1–2 周接入） | 自有库 |
| Clerk | 想最快上线、接受按 MAU 计费 | 低 | 第三方 |

**实际表结构（已实现，见 `lib/db/schema.ts` 与 `db/migrations/0000_black_medusa.sql`）**：

| 表 | 说明 |
| --- | --- |
| `user` / `session` / `account` / `verification` | **Better Auth 1.7.x 官方四表**（camelCase 列名；不要改成 `users`/`user_id`） |
| `workflows` | `id uuid`、`owner_id text fk user`、`graph jsonb`、`version int`、`is_public` |
| `workflow_versions` | `(workflow_id, version)` 唯一，保留历史图与作者 |
| `runs` | `status` 枚举 `run_status`、`token_usage jsonb`、`cost_usd numeric(10,4)` |
| `run_events` | `id bigserial`、`(run_id, seq)` 唯一，按序回放 SSE 事件 |

**关键索引**：`workflows(owner_id, updated_at desc)`、`GIN(workflows.graph)`、`runs(workflow_id, started_at desc)`、`runs(user_id, started_at desc)`、`run_events(run_id, seq)`、`account(provider_id, account_id)` 唯一。

**执行与回滚**：`pnpm db:generate` / `db:check` / `db:migrate`；迁移前 `pg_dump`，回滚优先备份恢复。完整说明见 `docs/agent-builder-hunyuan-20261111/05-持久化阶段A建表说明.md` 与 `db/README.md`。

**按拓扑的存储落位（已定案）**：PG `PGDATA` 从 V2 迁到 V3 NVMe（当前仅 9%），WAL 同盘；V2 仅保留基础备份/WAL 归档与 GitBucket；V1 保留模型母本。理由：V2 为 4×8T HDD RAID6，随机写延迟会直接成为应用 P95 瓶颈。V1/V2 同属一个 RAID6 池，备份必须异机（yyc3-22 外置 NVMe + 对象存储），否则池故障会同时丢失模型、库与备份。迁移执行单见 `docs/06-运维保障阶段/0601-运维策略/006-PGDATA迁移至V3执行单.md`（停机 rsync / `pg_basebackup` 预拷贝 / `initdb` 逻辑迁移 + 回滚）。

**分阶段迁移**：

1. **阶段 A（已完成）**：建表 + 连接模块 + SQL 迁移；Better Auth 兼容账号表。
2. **阶段 B（已完成）**：`/api/workflows` CRUD、Better Auth 登录、执行写 `runs`/`run_events`、前端「云端」保存/加载；执行 API 为「会话 + 令牌」双模。
3. **阶段 C（待启动）**：团队/空间、公开模板、版本回滚 UI、运行回放、配额与审计。

**验收标准**：跨设备可恢复工作流；执行记录可按 run 回放节点事件；未登录用户仍可匿名试用但受限流约束。

### 3.3 引擎抽离（已完成）

**改造前**：`app/api/execute-workflow/route.ts` 约 605 行，执行逻辑与 HTTP/SSE 耦合，无法单测、无法复用。

**改造后**：

- `lib/workflow-engine.ts`：纯函数式内核，入参 `{ nodes, edges, onUpdate, maxDepth }`，返回 `ExecutionResult[]`；不依赖 Next.js。
- `app/api/execute-workflow/route.ts`：仅保留鉴权、请求体/图规模校验、SSE 封装与日志，约 100 行。
- 行为保持：原有 13 个 API 级用例全部通过；新增引擎级用例覆盖事件序列、分支跳过、环图深度。

**收益**：可被 CLI / 定时任务 / 批处理复用；后续接持久化只需在调用处写 `runs`，不触碰节点逻辑。

**残余**：`lib/code-generator.ts` 仍有一份图遍历/插值逻辑，下一步统一复用 `interpolateVariables`，避免双实现漂移。

### 3.4 三个占位节点真实现（已完成）

| 节点 | 旧实现 | 新实现 | 关键约束 |
| --- | --- | --- | --- |
| `imageGeneration` | `generateText` 从 `files` 里捞图 | `generateImage({ model, prompt, aspectRatio })`，输出 `data:image/png;base64,...` | 模型前缀路由：`openai/` / `google/` / 其他走 Gateway 字符串；25s 超时 |
| `audio` | 返回 `notImplemented` | `generateSpeech({ model: openai.speech(id), text, voice })`，输出 `audio/mpeg` data URL | 文本空值明确报错；data URL 体积大，生产建议转对象存储 |
| `embeddingModel` | 返回 `notImplemented` | `embed({ model: openai.embedding(id), value })`，输出向量 + 维度 + usage | 维度随模型变化（1536/3072） |
| `structuredOutput` | 返回 `notImplemented` | `generateText({ output: Output.object/array({ schema: jsonSchema(...) }) })` | v7 已移除 `generateObject`；schema 非法/缺 prompt 均明确报错 |

**前端补齐**：`structuredOutput` 配置面板新增 JSON Schema 与兜底 Prompt 输入（原面板只有 schemaName 与 mode，实际无法配置 schema）。

**遗留优化**：音频/图片以 data URL 直接在 SSE 传输，长音频会放大消息体；下一阶段改为「上传对象存储 + 返回短 URL」，并把 `run_events` 只存引用。

### 3.6 多实例限流外置（已完成）

**实现**：`lib/rate-limit-store.ts`

- 接口 `RateLimitStore.hit(key, limit, windowMs, now)`；
- 默认 `MemoryRateLimitStore`：进程内滑动窗口，超 500 桶惰性清理；
- 配置 `UPSTASH_REDIS_REST_URL/TOKEN`（兼容 `KV_REST_API_*`）后切换 `RedisRateLimitStore`：
  - 单次 `EVAL` 完成 `ZREMRANGEBYSCORE → ZCARD → ZADD → PEXPIRE`，避免多往返竞态；
  - 排序集合天然滑动窗口，避免固定窗口边界双倍突发；
  - 远端异常默认 **fail-open**（放行 + 60s 限频告警），可用 `RATE_LIMIT_FAIL_MODE=closed` 改为拒绝。
- `lib/api-guard.ts` 改为 `await checkRequest(req)`，调用方无感切换；
- `/api/health` 暴露 `rateLimitStore` 便于确认部署拓扑是否生效。

**验证**：新增 `rate-limit-store.test.ts`（8 例）与 guard Redis 路径用例；`pnpm test` 224 全绿。

**残余**：Redis 故障时 fail-open 意味着短时无保护，需配合网关层（nginx `limit_req` / 云 WAF）做第二道限流。

## 四、残余风险登记

| 风险 | 等级 | 触发条件 | 缓解 |
| --- | --- | --- | --- |
| Redis 故障期间限流失效 | P1 | Upstash 网络/配额异常 | 网关层二次限流；`RATE_LIMIT_FAIL_MODE=closed` 可选 |
| 音频 data URL 撑大 SSE | P2 | 长文本 TTS | 改对象存储 + 短 URL |
| image/audio 真实调用未做费用熔断 | P1 | 恶意高频调用 | 令牌 + 限流 + Provider 侧预算告警 |
| standalone 多实例缓存不一致 | P2 | 水平扩容且使用 ISR | 自定义 cacheHandler + Redis |
| 持久化未落地前的数据丢失 | P2 | 用户清缓存/换设备 | 阶段 A 尽快上线导入 |
| 文档再次超前于代码 | P3 | 批量生成 stub | 「写一个补一个」+ PR 检查清单 |
